# creator.dm

TikTok Shop のクリエイターへ複数アカウントから DM を送付する運用を、一元管理するための社内ツールです。

- 運用者 10 名 × 1 人あたり 10 アカウント程度（合計100アカウント）の運用を想定
- 日次の送付数・返信数を運用者が手入力し、そこから報酬・アラート・転換率を自動で算出します

## 画面はDM送付者用と管理者用で完全に分かれています

ログインすると役割に応じた画面に振り分けられます。DM送付者が管理画面のURLを直接開いても
自分の入力画面に戻されるため、他の人の実績や報酬設定が見えることはありません。

### DM送付者の画面（`/my`）

毎日の入力に集中できるよう、サイドバーのない4タブ構成にしています。

| タブ | 内容 |
| --- | --- |
| 今日の入力 | 自分のアカウントごとに送付数・返信数・メモを入力。入力しながら合計・返信率がその場で更新され、返信数が送付数を超えていると保存できません。下に直近7日の入力状況が並び、未入力の日は赤く表示され、そのままタップして遡って入力できます |
| 自分の実績 | 自分の送付数・返信率・30日推移・ファネル・アカウント別の内訳・月別の実績と報酬見込み |
| 返信者管理 | 返信があったクリエイターを登録し、LINEに誘導できたら日付を入れる。入力するのは**クリエイターID・送付アカウント・返信日・LINE誘導日の4項目だけ**。**LINE登録の確認**と面談は管理者が記録するため、ここでは参照のみ |
| 送付文章 | **初回DM**と**返信後のトーク文**の2種類を管理。確認・コピー・編集ができ、保存すると新しい版になり前の版に戻せます |

### 管理者の画面

| 機能 | 画面 | 内容 |
| --- | --- | --- |
| 全体管理 | ダッシュボード | 全運用者の送付数・返信率・報酬見込みを1画面で俯瞰。日次推移とファネルも表示 |
| アラート | アラート | 返信率の低下、日報の未入力、送付ゼロのアカウント、LINE転換率の低下などを自動検知 |
| 月間報酬管理 | 報酬管理 | 運用者ごとに異なる単価で自動計算。確定／支払済のステータス管理と、賞与・控除の調整に対応 |
| リード管理 | リード管理 | 全運用者のリードを横断で確認・修正。**LINE登録の確認と面談実施の記録はここで行う**（有無のチェック＋日付、または一覧のボタンでワンクリック） |
| 送付文章の管理 | 送付文章 | 全運用者の文面を確認・編集。**初回DM／返信文**の2種別に対応し、変更履歴も参照できます |
| アカウント管理 | アカウント | TikTokアカウントの登録、稼働／停止／BANの管理、送付目標の設定 |
| 代理入力 | 日報の代理入力 | 送付者が入力できないときに、管理者が代わりに登録・修正する |
| メンバー・単価 | メンバー・単価 | 運用者の登録と、送付単価・ボーナス・月額固定の設定 |
| バックアップ | バックアップ | 毎日自動で取得した全データの控えを確認・ダウンロード。手動取得も可能 |

### 権限

| | DM送付者 | 管理者 |
| --- | --- | --- |
| 自分の日報・文章・リード | ○ | ○ |
| 他の人のデータ | × | ○ |
| 報酬管理・単価設定・メンバー管理・アラート設定 | × | ○ |

## 技術構成

- Next.js 16（App Router / Server Actions）+ React 19 + TypeScript
- PostgreSQL（`pg`）— Vercel の Storage から接続した Postgres をそのまま使えます
- 認証は HMAC 署名付き Cookie ＋ scrypt によるパスワードハッシュ（追加ライブラリなし）
- グラフは依存パッケージを使わず素の SVG で描画

テーブルはアプリの初回アクセス時に自動作成されます。スキーマを変更したときは
`src/lib/schema.ts` の `SCHEMA_VERSION` を上げると、次のアクセス時に差分が適用されます
（アドバイザリロックで直列化しているため、複数のインスタンスが同時に起動しても安全です）。
マイグレーションコマンドを実行する必要はありません。

## Vercel へのデプロイ

1. Vercel で **Add New → Project** から、このリポジトリを Import する
2. **Storage → Create Database → Postgres（Neon）** を作成し、このプロジェクトに Connect する
   - `DATABASE_URL` などの環境変数が自動で追加されます
3. **Settings → Environment Variables** に `APP_SECRET` を追加する（Production / Preview / Development すべてにチェック）
   - 値は次のコマンドで生成できます
     ```bash
     node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
     ```
4. **Deployments → Redeploy**（3で環境変数を足したあとに再デプロイが必要です）
5. 公開された URL を開くと初回セットアップ画面が出るので、管理者アカウントを作成する

以降は管理者でログインし、**メンバー・単価** から送付者を登録して運用を開始します。
`APP_SECRET` を後から変更すると、全員がログアウトされます（作り直す場合以外は変更しないでください）。

### デモデータを本番に入れたい場合（任意）

Vercel の Postgres の接続文字列をローカルの `.env` に書いてから実行します。運用開始前だけにしてください。

```bash
npm run seed:demo
```

## ローカルで動かす

```bash
npm install
cp .env.example .env    # DATABASE_URL と APP_SECRET を設定
npm run dev             # http://localhost:3000
```

`DATABASE_URL` には Vercel の開発用ブランチの接続文字列か、手元の PostgreSQL を指定します。
デモデータ（運用者10名 × 5アカウント × 約60日分）を入れる場合：

```bash
npm run seed:demo       # 運用者 op01〜op10 / パスワード password1234
```

## 環境変数

| 変数 | 用途 |
| --- | --- |
| `DATABASE_URL` | PostgreSQL の接続文字列。Vercel で Postgres を Connect すると自動で入ります（`POSTGRES_URL` でも可） |
| `APP_SECRET` | セッションCookieの署名鍵。**必須**。本番で未設定だとエラーになります |
| `SEED_ADMIN_LOGIN_ID` / `SEED_ADMIN_PASSWORD` | `npm run seed` で作る初期管理者。画面からセットアップする場合は不要です |
| `DB_POOL_MAX` | 接続プールの上限（既定 5）。通常は変更不要です |
| `CRON_SECRET` | 日次バックアップの実行APIを保護する任意の文字列。設定すると Vercel からの呼び出しだけを受け付けます |
| `ADMIN_RESET_TOKEN` | 管理者ログインの復旧画面（`/recover`）を開くための合言葉。**普段は設定しないでください**（未設定なら画面ごと存在しません） |

## 運用のながれ

1. 管理者が **メンバー・単価** で送付者を登録し、DM単価・ボーナス・月額固定を設定する
2. 管理者が **アカウント** に TikTok アカウントを登録する（1日の送付目標も設定可）
3. 送付者が毎日 **今日の入力**（`/my`）で送付数・返信数を入力する
4. 送付者が返信のあったクリエイターを **返信者管理** に登録し、LINEに誘導できたら日付を入れる
5. 管理者が **リード管理** で、実際にLINE登録されたかを確認し、面談の実施を記録する

送付者が入れる「LINE誘導日」は**申告**、管理者が入れる「LINE登録」は**確認**で、別々に記録されます。
報酬のLINEボーナスと、ダッシュボードの「LINE登録」件数は、**管理者が確認したもの**を集計します。
6. 管理者が **アラート** で返信率の悪化や入力漏れを確認し、必要なら **送付文章** を見直す
7. 月末に **報酬管理** で金額を確認し、確定 → 支払済 にする

### 単価の考え方

報酬は次の式で計算されます。

```
送付数 × DM単価
  + 返信数   × 返信単価
  + LINE登録数 × LINEボーナス
  + 面談実施数 × 面談ボーナス
  + 月額固定
  + 調整（賞与・控除など）
```

単価は「適用開始月」つきで登録されるため、単価を変更しても過去の月の金額は変わりません。
使わない項目は 0 のままにしておけば計算に影響しません。

### アラートの閾値

**アラート設定** から変更できます。初期値は次のとおりです。

| 項目 | 初期値 |
| --- | --- |
| 判定対象期間 | 直近 7 日 |
| 判定に必要な最低送付数 | 50 件 |
| 返信率の注意ライン / 危険ライン | 8% / 5% |
| 日報未入力の警告日数 | 2 日 |
| LINE転換率の注意ライン | 20% |

送付数が「最低送付数」に満たない期間は、母数が小さく率が安定しないため返信率の判定をスキップします。

## バックアップと復元

不具合や誤操作でデータが失われても戻せるよう、3段構えにしています。

### 1. アプリの日次バックアップ（自動）

毎日 **日本時間の朝5時** に全テーブルをJSONにまとめ、gzip圧縮してデータベース内に保存します。
直近30件（約1か月分）を保管し、古いものから自動で削除されます。

管理画面の **バックアップ** から、取得履歴の確認と、任意の時点のJSONダウンロードができます。
「今すぐバックアップ」でその場で取ることもできます。

自動実行は `vercel.json` の `crons` で設定済みです。デプロイすれば有効になります。
外部から叩かれないようにするには、Vercel の環境変数に `CRON_SECRET`（任意のランダム文字列）を
追加してください。設定すると Vercel からの呼び出しだけを受け付けます。

最後の取得から時間が空くと、バックアップ画面に警告が出ます。

### 2. データベース自体の復旧（Neon）

Vercel の Postgres（Neon）には過去の時点に巻き戻す機能（Point-in-time restore）があります。
データベースごと壊れた場合はこちらを使います。保持期間はプランによって異なるため、
Vercel の Storage → データベース → Settings で確認してください。

### 3. 手元への控え

長期保管したい場合は、バックアップ画面からJSONをダウンロードして保存するか、次を実行します。

```bash
pg_dump "$DATABASE_URL" > backup/creator-dm-$(date +%Y%m%d).sql
```

### 復元のしかた

管理画面の **バックアップ → バックアップから復元する** で、ダウンロードしたファイル
（`.json` / `.json.gz` のどちらでも可）をアップロードすれば戻せます。
**現在のデータは全て置き換わります。** 実行前に必ず今の状態のバックアップを取ってください。
確認のため「復元する」と入力しないと実行されません。
復元は1つのトランザクションで行うため、途中で失敗した場合は元の状態に戻ります。

ターミナルから実行することもできます。

```bash
npm run restore -- backup.json           # 中身の確認だけ（何も書き換えない）
npm run restore -- backup.json --apply   # 実際に復元する
```

`DATABASE_URL` が復元先を指していることを確認してから実行してください。

### データベースを別のものに引っ越す

地域を変えるときや、別のサービスに移すときの手順です。画面だけで完結します。

1. 管理画面の **バックアップ** で「今すぐバックアップ」→ 一覧から **.gz** をダウンロード
2. 新しいデータベースを作る（地域は東京 `ap-northeast-1` を選ぶ）
3. Vercel の環境変数 `DATABASE_URL` を新しいものに差し替えて再デプロイ
4. 開くと初回セットアップ画面になるので、**仮の管理者**を作ってログイン
5. **バックアップ → バックアップから復元する** で 1 のファイルをアップロード

仮の管理者は復元時に上書きされて消えるため、引っ越し後は元のIDとパスワードでログインします。
リードやアカウントのID（採番）も引き継がれるので、そのまま運用を続けられます。

## 管理者のログインが分からなくなったとき

ログインは**メールアドレスではなくログインID**です。パスワードは scrypt で
ハッシュ化して保存しているため、データベースを見ても元の文字列は分かりません。
**思い出すのではなく、設定し直します。**

### 画面から復旧する

1. Vercel の **Settings → Environment Variables** に `ADMIN_RESET_TOKEN` を追加する
   （16文字以上のランダムな文字列。Production にチェック）
   ```bash
   node -e "console.log(require('crypto').randomBytes(24).toString('hex'))"
   ```
2. **Deployments → Redeploy** で再デプロイする
3. `https://<本番URL>/recover` を開き、1で設定した合言葉を入力する
4. 登録されているログインIDの一覧が出るので、対象のIDに新しいパスワードを設定する
   （そのままログインした状態になります）
5. **`ADMIN_RESET_TOKEN` を削除して再デプロイする**

`ADMIN_RESET_TOKEN` が未設定のとき、`/recover` は 404 になり存在しません。
復旧が終わったら必ず消してください。

### ターミナルから復旧する

`DATABASE_URL` が手元にある場合は、こちらのほうが簡単です。

```bash
npm run reset-password                          # 登録されているIDの一覧
npm run reset-password -- admin 新しいパスワード   # パスワードを設定し直す
```

## 表示を速く保つための決まりごと

画面の待ち時間は、ほぼ「データベースとの往復回数 × 1往復の時間」で決まります。
処理そのものは1画面あたり数ミリ秒しかかかっていないため、次の2点だけ守れば速さは保てます。

1. **ページの読み込みは `Promise.all` でまとめる。** `await` を縦に並べると、
   1本ずつ順番に往復するので待ち時間がそのまま積み上がります。
   現在はどの画面も往復2回（ログイン確認＋データ読み込み）に収めています。
2. **一覧の中で1件ずつ引かない。** 行ごとに `await` すると件数分の往復になります。
   先に一覧を1本で引いて `Map` にしてから引き当ててください。

そのほかの仕組み：

- ログイン中のユーザー情報とアラート件数は、数秒〜60秒だけプロセス内に保持します
  （メンバーの停止・権限変更・アラート閾値の変更は、その場で破棄して即反映します）。
- サイドバーのアラート件数は本文とは切り離して後から差し込むため、
  集計を待たずに画面が出ます。
- 画面を切り替えると、サーバーの応答を待つ間に骨組み（グレーの帯）が出ます。
  ボタンが効いていないように見えるのを防ぐためのもので、押した直後に切り替わります。

**関数とデータベースの地域を揃えてください。** `vercel.json` で関数を東京（`hnd1`）
に固定しています。データベースが別地域（例：`us-east-1`）だと、1往復ごとに
100ミリ秒以上が上乗せされ、上の工夫がすべて帳消しになります。

実際にどれだけかかっているかは、管理画面の **アラート設定 → データベースとの往復時間**
で測れます（「測定する」を押すと、本番のサーバーから実測します）。目安は次のとおりです。

| 1往復の中央値 | 判定 | 対応 |
| --- | --- | --- |
| 15ms 未満 | 近い | 理想。対応不要 |
| 15〜60ms | やや遠い | 実用上は問題なし |
| 60ms 以上 | 遠い | データベースを東京（`ap-northeast-1`）に作り直して繋ぎ替える。もしくは `vercel.json` の `regions` をデータベース側に合わせる |

## 補足

- 日付は常に日本時間（JST）基準で判定します。
- DM の送付数・返信数は運用者による手入力です。TikTok からの自動取得は行いません。
